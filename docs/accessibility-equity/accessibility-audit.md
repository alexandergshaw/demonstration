## Primary research and product implications

These sources supply standards and learning-design evidence. They do not establish that Leading Educators has commissioned each feature.

1. [W3C WAI modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) recommends initial focus on a static top element for long structured content, and return to the invoking control on close. This directly supports the verified Guide repair. APG is implementation guidance, not a standalone conformance standard.
2. [WCAG 2.2 labels or instructions, 3.3.2](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html) explains that input rules and required-field cues help people avoid errors. [Headings and labels, 2.4.6](https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html) supports descriptive control labels. Apply these to owner, agenda, and evidence toggles.
3. [Resize text, 1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) calls for text to resize to 200% without loss. [Reflow, 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) concerns 320 CSS pixel width for horizontal-language content. Small default type is not automatically a failure; fixed pixel typography does, however, make a simple root-font preference ineffective. Use relative typography and verify actual rendered enlargement and reflow.
4. [Text spacing, 1.4.12](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html) requires no loss when users override line, paragraph, letter, and word spacing to the stated thresholds. It does not require a built-in spacing button. A reader preference is an additional convenience; layouts must remain resilient even without it.
5. [Status messages, 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) supports programmatically exposed save, error, and success messages without unnecessary focus shifts. Preserve existing status and alert behavior; new preference-storage errors should have equivalent treatment.
6. [Contrast minimum, 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) distinguishes ordinary text's 4.5:1 threshold from large text's 3:1. [Target size minimum, 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) sets a 24 CSS pixel minimum with exceptions. Preserve the app's larger targets and readable default contrast; a separate contrast widget is not necessary to satisfy either criterion.
7. [Animation from interactions, 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) supports honoring reduced-motion preferences. This is AAA, and the current app has little nonessential motion. Native preference support is sensible resilience, not evidence of a current animation failure.
8. [CAST UDL Guidelines 3.0](https://udlguidelines.cast.org/) centers learner agency across engagement, representation, and action/expression. Its [display customization consideration](https://udlguidelines.cast.org/representation/perception/customize-display/) supports optional larger type and roomier spacing. Keep this browser-local, avoid changing instructional approvals, and handle blocked storage gracefully.
9. CAST's [languages and dialects consideration](https://udlguidelines.cast.org/representation/language-symbols/languages-dialects/) values multiple linguistic resources and clarified vocabulary. Its [expression bias consideration](https://udlguidelines.cast.org/action-expression/expression-communication/bias/) cautions against treating written communication as inherently more rigorous. In this fraction task, ask educators to separate mathematical understanding from English proficiency or response-format barriers, and plan aligned alternatives such as diagrams or oral explanation. Do not infer student identities from the two fictional quotations.
10. CAST's [exclusionary practices consideration](https://udlguidelines.cast.org/action-expression/strategy-development/exclusionary-practices/) supports planning for barriers rather than attributing difficulty to fixed student deficits. A practical product inference is a leader-authored access/participation check: whose evidence is absent, which task barriers could matter, and how the team will hear different voices. Carry those choices into meeting materials rather than awarding an unvalidated equity score.

## Recommended implementation and acceptance scope

- Repair the three verified findings.
- Add opt-in larger text and spacing preferences, independent of cycle data and approvals. Check persistence, corrupt/blocked storage, and ability to return to default.
- Add concise, contextual equity prompts and a leader-authored participation/access plan. Preserve mathematical rigor and human judgment. Avoid demographic filters, automated bias ratings, diagnostic inferences, or an unsupported claim of full translation.
- Test keyboard entry/exit, locked-stage guidance, validation focus, source selection names, 320px layout, enlarged typography, dialog scrolling, and long authored content. Check that preference changes never invalidate or erase plans.
- Treat actual screen-reader behavior, operating-system forced colors, native 200%/400% browser zoom, and offline print as unverified unless directly exercised. DOM/AX inspection alone cannot certify assistive-technology compatibility.
